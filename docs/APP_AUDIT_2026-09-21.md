# Video Target Finder 全体走査・改修基準

更新日: 2026-09-21

## 目的

このアプリの最終目的は、長い動画から「推し」が映っている場面を見つけ、不要な場面を除外し、短いまとめ動画をできるだけ簡単に作ること。

通常利用の主動線は次の5ステップに固定する。

1. 動画を選ぶ
2. 推しの見本画像を選ぶ
3. 推しの登場場面を探す
4. 候補を正解 / 誤検出で確認する
5. 推し動画を作る

探索間隔、Feature Print distance、tracking、粗探索候補、診断ログ、認識精度レポート等は開発・調整には必要だが、通常操作の主役にはしない。

## 実測上の重要課題

直近のダニエル検証では、判定済み候補で正解17 / 誤検出24。正例と負例のFeature Print distance分布が重なっており、単純なしきい値変更だけでは大幅改善しにくい。

平均trackingは高いため、現時点の主な認識ボトルネックは区間追跡より「1フレームを対象らしいと判定する特徴表現」。

認識エンジン強化はUI整理と分離して検証する。

## Stage 19 方針

- メイン画面を5ステップ化

## 2026-09-21 再走査で追加確認した事項

- 正規 v0.18.0 の通常画面には 1→2→4→5→6→8 と見える番号不整合が残っていた。v0.19候補では5ステップへ統一する。
- 認識レポートの累積「Feedback-rescan added」と短評の「前回追加数」が別定義だった。v0.19候補では再探索を #1 / #2 ... の単位で保持し、初回・各回・累積を分離する。
- 標準初回探索は粗探索上位18地点を保持する一方、学習再探索は最大72地点まで保持する。再探索で大量に候補が増える原因はFeature Printの識別力だけでなく、この候補予算差も含み得る。
- ただし候補上限を直ちに増やすと詳細探索量・発熱・時間が増えるため、実動画ベンチマークなしには変更しない。次の認識評価では候補予算を独立変数として比較する。
- v0.18.0 CIのSwift 6ビルドでは、ソース由来の並行処理warningは確認されず、AppIntents未使用に伴うmetadata extraction warningのみ。
- Photos直接保存経路は現ソースに存在せず、requestPlayerItem + アプリ内永続保存 + Share Sheet経路を維持する。


## Stage 20 / v0.20 評価基盤

v0.19の再走査で、標準初回探索は詳細探索へ18候補を送る一方、学習再探索は最大72候補を保持することを確認した。

この差を解消するために初回詳細探索を単純に72件へ増やすと、詳細フレーム生成・Feature Print比較・発熱・処理時間が増え、認識エンジン自体の効果と候補数の効果を分離できなくなる。

そのためv0.20では次の方式を採用する。

- 初回の通常ScanCandidateリストと実際の詳細探索予算は従来どおり維持する（標準18件）
- 粗探索ではサムネイルを持たない時刻＋distanceだけの軽量reserveを別途保持する（標準最大72件）
- 通常の詳細探索は従来のScanCandidate 18件だけを使用し、reserveは探索処理へ渡さない
- 再探索で新たに正解となった区間について、初回reserveの順位を後から照合する
- 初回上位18件に入っていたのに見逃した場合: 詳細しきい値・追跡・区間化側を疑う
- 19〜72位に入っていた場合: 初回候補予算が見逃し要因の可能性
- 初回reserveにも無い場合: 粗探索間隔またはFeature Print特徴表現を疑う

この評価は因果を断定するものではなく、次のA/Bテストで変更する変数を絞るための診断指標として扱う。

### 回帰上の制約

- 分析用reserveを増やしても初回詳細探索件数を増やさない
- checkpoint v2でreserve由来を識別する
- v1 checkpoint復旧時は候補予算分析を無理に有効化しない
- 旧v0.19以前の認識レポートはOptional追加項目により読み込み互換を維持する
- 認識エンジン名は現時点で Apple Vision Feature Print と明示する
- 将来のembedding比較では同じレポートスキーマを使用する


### 追加再検証: reserveの完全分離

最初のv0.20候補では、詳細探索は18件に制限したまま粗探索のScanCandidate自体を72件保持していた。この方式でも詳細探索量は増えないが、次の2点がv0.19と異なる。

- 最大72枚の候補サムネイルを粗探索中に保持するため、ピークメモリが増え得る
- 72件を保持する候補リストと18件を保持する候補リストでは、時刻近接候補の置換履歴が理論上完全同一とは限らない

このため正規反映前に再設計し、通常ScanCandidateは従来どおり感度別12/18/24件のまま、分析用reserveだけをCandidateBudgetPoint（time/distance）として独立管理する方式へ変更した。

これによりv0.20で増えるのは軽量な分析メタデータのみで、詳細探索対象・通常候補サムネイル数・初回候補選択ロジックはv0.19相当を維持する。


## v0.20.1 / Build 21 永続化再走査

v0.20正規版の再分析で、ScanCheckpointStore.clear() が Application Support/VideoTargetFinder フォルダ全体を削除していることを確認した。

同じフォルダには次の永続データも存在していた。

- recognition-quality-report.json
- diagnostic.log
- scan-checkpoint.json
- checkpoint-references/

そのため、動画変更・見本画像変更・粗探索完了・チェックポイント破棄の各タイミングで ScanCheckpointStore.clear() が呼ばれると、チェックポイント以外の認識レポートと診断ログも削除される。savedRecognitionReport は現セッションのメモリ上には残るため、その場では気付きにくいが、アプリ再起動後のレポート復旧と過去診断ログを失う。

### 修正方針

- Application Support/VideoTargetFinder は共有ルートとして維持する
- PersistentStorageLayout を追加し、各永続ファイルのパス定義を一元化する
- ScanCheckpointStore.clear() は scan-checkpoint.json と checkpoint-references/ だけを削除する
- recognition-quality-report.json と diagnostic.log は保持する
- 一時ディレクトリ上で4種類を作成し、checkpoint clear後にレポート/ログだけ残ることを自動テストする
- 回帰検査で removeItem(at: rootURL) の再導入を禁止する


### 候補予算診断の不変条件検証

軽量reserve方式では通常ScanCandidateとreserveを別リストとして同時更新するため、設計上は通常候補N件とreserve上位N件が一致する。しかし候補予算診断は「reserve順位N位以内=実際に詳細探索された」と解釈するため、この一致を推測だけに依存させない。

v0.20.1では粗探索完了時に通常候補をtime/distanceへ変換し、reserve先頭との一致を実行時検証する。時刻またはdistanceが許容差を超えてずれた場合、候補予算分析を無効化し、誤った「18位以内/19位以下」判定をレポートへ出さない。

中断復旧時はさらに、保存済みanalysisReserveが存在することも必須条件とする。旧checkpointや不完全なreserveから原因分類を推測しない。
